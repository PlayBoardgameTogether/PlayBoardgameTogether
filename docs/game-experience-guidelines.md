# 桌游体验开发指南

适用于新游戏接入、既有游戏棋桌改进，以及与操作反馈、结算、成长相关的体验设计。目标是：**尽可能还原并改善实体桌游的物件与氛围，用精美画面和有意义的动画发挥电子版优势；手机上操作顺手，电脑上纵览全局；每一步有反馈，每一局看得见成长。**

本文补充 [UI/UX 设计规范](ui-ux-guidelines.md)，实现入口与回归方式分别见 [界面系统](ui-system.md)、[UI 开发与回归](ui-development.md)。安全、身份、隐私、事务与测试隔离遵守 [AGENTS.md](../AGENTS.md)。设计建议可按游戏类型调整；本文不表示已实现所列能力，也不授权一次性改造所有游戏或新增成就系统。

## 开发前确定核心体验

按任务规模简要说明玩家本轮需要理解什么、比较什么、选择什么，以及怎样知道行动成功。已有方案直接复用，不重复产出设计稿。

- 明确影响决策的必要信息：公共局面、本人手牌或资源、合法行动、代价和可公开的结果。
- 分别安排手机与电脑的内容顺序、主要操作位置；选择与棋盘结构相适应的横竖屏方案。
- 明确本轮要改善的行动反馈、单局收获或长期成长，不把装饰动画、徽章数量当作体验目标。
- 先打磨一款游戏的完整流程，再提炼确有复用价值的能力，不要求其他游戏照搬同一棋桌。

## 先画清楚，再实现棋桌

新游戏或较大棋桌改版应先核对用户指定的实体版、规则和可用物件参考，列出“实体物件 → 数字画面 → 可交互状态”的对应关系。不同版本有差异时明确采用哪一版；资料不足的部分标记待核实，不把想象的物件或规则写成原版事实。

- 先提供桌面和手机布局图、一个有代表性的棋桌画面，以及本轮核心物件的图稿或状态示意；已有确认设计直接复用。用图说明空间与操作，不能只交一段配色描述或一组 emoji。
- 美术方向先明确时代、地域、材质、光照、视角和色板，再制作图标、场景、棋盘、卡牌和资源；同一游戏保持统一，不拼接风格不一的库存图。
- 美术资源属于正式交付内容。占位图、程序随手拼出的简陋几何图和 emoji 可用于验证原型，不能当作精美正式画面交付。SVG、Canvas、CSS 绘制或图片生成均可采用，以实际质感、辨识度和性能判断，不以技术形式代替美术质量。
- 具体游戏的图稿、原始素材、导出文件、状态映射与许可说明在该游戏独立仓库维护；平台只维护通用展示能力。遵守[分仓规则](game-repositories.md)，不直接修改主仓库的锁定游戏副本。

## Logo、封面和横幅分别设计

游戏标识必须在真实界面尺寸下清晰、完整、与背景协调。当前大厅展示分别使用 `iconUrl`、`coverUrl`、`backgroundUrl`，入口见[资源](assets.md)；以下为制作与验收要求，不表示平台已自动生成适配图。

| 用途 | 构图与展示要求 |
| --- | --- |
| 游戏图标 / Logo | 方形图标单独构图，主体足够大，小尺寸仍可辨认；横向字标按原比例另用合适容器，不压进方形槽 |
| 大厅封面 | 通常采用 16:9 场景或物件组合，裁切后仍有明确主体，不将小 Logo 拉伸成整张封面 |
| 详情横幅 / 背景 | 宽幅场景，为标题和按钮留出阅读区；分别检查手机与电脑的裁切焦点，必要时制作不同构图 |
| 棋桌物件 | 按实际落位、缩放和选中状态绘制，轮廓、方向与交互区域对应，不能直接复用封面当操作棋盘 |

- 透明标识保留真实透明通道，不烘焙白底、白边或不属于设计的厚阴影；有意设计的不透明徽章可保留，但必须与页面协调。检查源文件内部留白，不能仅靠放大 `<img>` 掩盖主体过小。
- 图标与完整字标通常等比完整展示（如 `object-fit: contain`）；场景图可按焦点裁切（如 `cover`）。不能拉伸变形、切掉标识关键部分，或用同一宽幅图机械套入所有槽位。
- 在亮、暗背景和真实小尺寸下检查清晰度、边缘与对比，避免白色方块套圆角卡片、重复边框和重阴影喧宾夺主。
- 横幅的主题场景应看得见，不把整张画面统一淡化成几乎不可辨认的水印。通过文字侧局部遮罩、留白和构图保证阅读，保留另一侧主体的色彩与细节。

**2026-10-25 用户截图反例**：波多黎各的横向港口插画塞入方形白色容器，上下明显留白且外层阴影很重；宽幅帆船背景过淡，无法撑起主题。后续应分别准备适合方形槽的标识和具有明确焦点的港口横幅，并在实际标题区验收。此处记录的是待改进标准，不代表本轮已替换图片或修复页面。

## 让实体物件成为数字棋桌的主体

尽可能保留实体版物件的辨识特征、空间关系和操作含义，并通过细节放大、合法目标提示、状态预览和动作反馈改善使用体验。不能把富有主题的棋桌退化为资源数字、文字表格和通用按钮；也不为了拟真保留难读文字、过小标记或不便触摸的尺寸。

以波多黎各为美术与交互示例，具体物件名称和数量以本次采用的规则版本为准：

| 物件 / 场景 | 画面要求 | 数字版可增强的体验 |
| --- | --- | --- |
| 货船与港口 | 画出船体、甲板、泊位和可辨认的货舱，不用一行“船：3/5”代替船只 | 直接在船旁表达货物类别、已装数量、剩余容量与合法装载目标；装船后可见货物从来源落到对应舱位 |
| 殖民所与人员船 | 结合所采用版本画出建筑、船只与人员位置；空位、占用和可分配状态清楚 | 点选人员再选位置，显示分配预览与剩余数量；不只靠小圆点或 emoji 表达全部状态 |
| 种植园、城市与建筑 | 有可区分的田地、作物、建筑轮廓与材质，保持实体板块的归属和布局关系 | 放大查看效果、费用和运转状态；建设或启用时呈现明确落位与状态变化 |
| 商品、钱币与计分物件 | 用统一风格的货箱、桶、钱币或标记表现，搭配清楚的类别与数量 | 拿取、生产、交易与计分能看出来源、去向和数量变化，不让装饰遮住数值 |
| 主题环境 | 港湾、海面、帆船、田地和建筑共同体现所采用版本的波多黎各殖民地经营背景 | 通过景深、光照和局部动态建立氛围，操作区域与背景分层，不能用通用木纹或一张淡图代替整套场景 |

上表是实现方向，不新增或改变规则。物件的空闲、选中、合法目标、不可用、已占用与处理中状态按需要设计；玩家应能把画面中的对象与自己的行动对应起来。

## 图片丰富、精美，少用 emoji

- 按游戏列出资源清单，覆盖主要棋盘区域、核心物件类别、关键卡面、资源和必要状态。优先补齐玩家反复观察、比较和操作的物件，不只制作入口封面；不以图片张数凑量，也不靠重复背景图制造丰富感。
- 核心游戏物件、角色、资源和行动图示优先使用专门绘制的插画、矢量图或统一图标。emoji 不作为正式棋子、货物、建筑、船只或主要按钮的默认图形；聊天中的玩家表达不受此限制。
- 美术表现游戏背景：例如波多黎各采用与所选版本相符的港口、种植园、船只与建筑语言。平台大厅的像素装饰不要求所有游戏都变成低细节像素画，也不强制所有游戏采用写实或重型 3D。
- 图像负责辨识和氛围，文字负责名称、数量、代价及规则效果；不能把关键状态只烘焙在图片中。提供必要的可访问名称，装饰图不重复播报，不能以 emoji 作为缺图回退。
- 素材需有可用来源与许可说明，不能因追求实体版还原直接提交未授权扫描件。导出合适分辨率和压缩版本，避免手机为小图标加载整张超大图；格式、配额、上传与 ZIP 限制分别遵守[资源契约](asset-contract.md)、[资源管理](assets.md)和[包格式](../apps/web/public/developer-docs/game-packages.md)，不能为美术绕过隔离或放宽校验。

## 双端共享规则，分别组织棋桌

两端使用同一权威规则、身份化 View 与正式动作链路，布局和输入方式可以不同。手机按任务重排内容；电脑利用空间支持局面比较。

| 内容 | 手机 | 电脑 |
| --- | --- | --- |
| 公共棋盘 | 保留行动所需局面，复杂区域可展开或缩放，并提供容易返回的总览 | 尽量完整展示，便于跨区域比较 |
| 本人手牌、资源 | 靠近底部，按需横向浏览，选中后仍能看见目标与代价 | 与公共区域同时可见，减少来回切换 |
| 对手信息 | 常驻影响决策的公开摘要，详情按需展开 | 空间允许时并列展示公开信息 |
| 行动操作 | 放在拇指容易触及的位置，选中后明确展示动作 | 支持点击与键盘；快捷键、悬停可作辅助 |
| 日志、规则、聊天 | 按需打开，关闭后保留选择与浏览位置 | 可用可收起的侧栏，避免挤占棋盘 |

不能为了窄屏隐藏关键决策信息。例如购买卡牌时，价格、本人资源和差额应容易同时比较；缩略、抽屉与分页不能让玩家靠记忆往返核对。需要公开比较的对手信息也不能一概收起。

不强制所有游戏使用同一方向。卡牌游戏可优先竖屏，空间关系复杂的大棋盘可提供横屏布局；不要把强制旋转作为所有手机玩家的唯一入口。缩放或平移不能成为读取常用文字、点击核心动作的前提。

固定操作区需避让系统安全区、浏览器界面与软键盘，不遮住目标、错误或行动结果。检查长昵称、大量手牌、文字放大及窄屏状态，不能只验证初始棋盘。

物件美术也需适配双端：电脑可同时铺开港口、城市与种植园，手机围绕当前阶段提供清楚的区域切换和必要总览，选中货物后仍能比较可装载船只及容量。小图保留简明轮廓和数量，大图展示材质与细节；不能把桌面画面整体缩小后让手机玩家辨认几像素的货舱。交互入口不能依赖 Hover，拖拽同时提供点选方案，横竖屏切换保留有效选择和浏览位置。

## 行动清楚，反馈可信

基本流程为：**选择对象 → 理解代价与效果 → 提交行动 → 看见实际结果。** 按误操作成本决定是否确认，简单且低风险的动作可以直接完成；稀缺资源消耗、结束回合等高成本动作提供清楚的确认。

- 选中状态不能只靠颜色；明确显示当前对象、可用目标、取消方式与不能行动的原因。
- 触摸区域原则上至少 44px，并与相邻动作保留间距；卡牌详情可点击查看，不能依赖悬停或长按才能发现。
- 拖拽可增强手感，同时提供点选对象再点目标的替代方式；核心流程也能用键盘完成。
- 提交前的本地草稿可取消。提交后是否可撤销由游戏规则决定，不能把清除本地选择当作撤销正式动作。
- 预览只使用本人 View 和公开信息，并标明是预览。涉及随机、秘密选择或对手响应时，不能承诺尚未确定的结果。
- 点击后立即显示选择或提交状态；只有权威确认后才呈现行动成功。提交中防止重复操作，结果未知时复用原请求查询回执，不生成新动作试探。
- 网络异常与恢复保持可见；恢复后同步权威局面，再让玩家继续决策，不能被旧草稿或旧动画覆盖。

例如花砖物语可在选砖后显示数量，选图案行后预览放入与溢出数量；真实结算时再展示移砖和得分来源。这是交互示例，具体合法性与提交语义仍由游戏负责。

## 成就感贯穿行动、单局与长期游玩

| 时间尺度 | 玩家应能理解什么 | 可选设计 |
| --- | --- | --- |
| 每次行动 | 自己的选择产生了什么效果 | 资源增减、完成一组、形成连锁、得分来源 |
| 每场对局 | 这局做成了什么、还能怎样提高 | 得分构成、可核验的关键回合、个人突破、再玩入口 |
| 长期游玩 | 自己积累了什么经验与身份 | 探索徽章、策略挑战、个人纪录、收藏与称号 |

优先解释局内反馈与结算，再按需求扩展长期系统。胜负之外也可展示有依据的进步，让未获胜的玩家理解自己的收获；不伪造安慰奖、策略评价或成长数据。

- 结算展示权威胜负与已提供的得分构成，保留最终棋盘及回顾入口，再由玩家决定返回或再玩。
- “最佳行动”“个人纪录”“提升多少”等判断必须有明确口径、可比较的数据与真实计算。只有总分时不能编造分项，缺失历史时不能推算纪录。
- 回顾和成就展示继续遵守身份与隐藏信息边界；对局结束不自动公开所有秘密。不得通过称号、条件进度或解锁提示间接泄露他人手牌和秘密选择。
- 长期目标优先鼓励掌握玩法、探索不同策略与友好协作。避免只奖励胜场或堆局数；检查目标是否诱导刷局、拖延、破坏合作或故意输赢。
- 称号、桌布、徽章等可作为展示奖励，成长奖励不改变公平对局中的规则优势；避免用断签惩罚制造游玩压力。

现有 [玩家徽章](badges.md) 已支持正式完成局数、不同游戏及指定游戏完成条件，还有管理员授予与自定义徽章。相关工作先复用该能力，不另建平行身份或成就链路；现有完成条件不代表已支持胜场、策略判断、永久解锁时间或即时解锁推送。

新增纪录或策略条件时，另行明确权威数据来源、精确游戏版本的适用性、重复处理与隐私边界；不能把客户端动画播放或点击次数作为正式授予依据。按实际需求扩展既有模块，不预先搭建奖励服务或改动对局事务。

## 沉浸感来自主题、反馈与节奏的一致

沿用 PlayBoard 暖阳大厅与深木棋桌基线。进入对局后让棋盘成为视觉中心，平台导航退到辅助位置；各游戏拥有自己的卡牌、棋子、材质、主题色与表现方式。

- 操作反馈：选牌、拿取、放置有清楚的选中和落位感，玩家知道操作作用于哪里。
- 结果反馈：资源移动有来源和去向，计分表达原因与数量；动效用于解释变化。
- 回合节奏：明确轮到谁、刚发生了什么、本人接下来需要做什么。等待时可以查看公开局面和最近行动，不用持续闪烁催促。
- 终局仪式：让必要的计分表现完成，最终局面与结果仍可查看；动画可跳过或缩减，不能迫使玩家等待才能继续。
- 手机性能：先保证点击、滚动和棋盘流畅，再增加纹理、阴影与装饰；按需加载资源，避免大量持续动画或以重型 3D 作为默认门槛。

电子版应主动利用动画解释实体桌游中需要玩家手动追踪的变化：例如货箱从仓库进入货舱、人员从船只落到岗位、建筑落位、钱币支付与得分汇入。优先实现本轮核心动作的完整反馈，不把按钮缩放或日志淡入当作全部游戏动画。主题需要时可加入轻微海面、帆影或环境光动态，但应低频、可停用，后台暂停，不抢占行动注意力。服务端结果先落实，动画可跳过、合并或中断；快速连步与新快照到达时不能堵塞输入、重复结算或把旧位置画回去。

声音可关闭，动效尊重 `prefers-reduced-motion`；关闭声音或减少动画后，文字与视觉状态仍能完整解释结果。无声、低性能及资源加载失败都不阻断行动。

动作动画与事件音效只消费本人获准的 View/投影事件。实时音效通过平台现有播放器与授权端口播放，按事件去重，区分 live/catch-up；刷新、重连、解除静音不能补播历史。回放可按既有表现通道播放动作动画，但不能因此获得实时音效授权。

已有客户端终局停留、节拍音效与回放表现能力见 [游戏 SDK](game-sdk.md)，声音生命周期见 [音频](audio.md)，历史视角见 [回放](replays.md)。先核对游戏类型与实际能力；在线 ZIP 的能力与限制以 [包格式](../apps/web/public/developer-docs/game-packages.md) 为准，不默认拥有内置游戏的全部表现接口。

## 平台与游戏的职责

平台复用连接与恢复、身份、菜单、设置、基础反馈和无障碍能力；游戏扩展拥有棋盘、卡牌、资源区、HUD、选择预览与主题表现。正式规则仍走现有 matches 事务，平台核心不增加具体 gameId 的规则分支。

选择状态、布局切换与动画进度属于客户端表现；分数、胜负和正式成长依据来自服务端权威事实。主题与素材复用现有 Token、CSS layer、资源管理及播放器，不建立平行主题、音频或传输系统。

## 按真实任务验收

按本轮影响选用以下检查，实际命令与测试范围遵守 [AGENTS.md](../AGENTS.md) 和 [UI 开发与回归](ui-development.md)。纯文档更新核对事实、链接与差异，不需要执行产品流程或业务测试。

| 验收问题 | 检查方式 |
| --- | --- |
| Logo 是否清楚且与界面协调 | 在列表、详情和适用房间入口的真实尺寸检查比例、主体大小、留白、透明边缘、裁切及亮暗背景；不能只看原图 |
| 画面能否体现这款桌游 | 对照所采用实体版参考核对核心物件、空间关系与主题；检查船只、建筑等是否仍被文字框或 emoji 占位替代 |
| 美术与动画是否进入真实流程 | 检查资源齐备、加载成功，以及选择、落位、生产或装载等本轮关键变化；重连不重播历史动作，缺图也能继续操作 |
| 手机能否顺手完成一回合 | 实际触摸或设备仿真检查选中、查看详情、目标选择、取消及提交；核对误触和遮挡 |
| 电脑能否快速比较局面 | 检查公共区域、本人资源和必要对手信息能否同时理解；验证键盘流程与焦点 |
| 两端能否理解行动和得分 | 检查正常、不可用、提交中、失败、结果未知和结算状态，反馈与权威结果一致 |
| 断线后能否可靠继续 | 按受影响范围验证原请求回执、权威快照恢复、旧选择处理及无历史音效补播 |
| 玩家能否看见真实收获 | 对照数据核验结算与成长展示；同时检查未获胜、并列或数据不足等适用情况 |
| 关闭装饰后是否仍可玩 | 检查静音、减少动态效果、主题对比、文字放大与资源失败回退 |

较大棋桌或布局改动覆盖桌面、笔记本与手机，例如 1440×900、1280×800、390×844；窄屏或横屏受影响时补查 320px 宽度、844×390 等相关尺寸。按游戏检查长手牌、多人信息与复杂局面，不能只截图初始状态。

记录实际页面、状态、视口、浏览器、仿真或物理设备、验证结果与未验证项。固定场景用于视觉检查，真实身份、房间和联机流程按现有 E2E 验证；截图、设备仿真或 mock 不能冒充实机和真人联机验收。

新游戏或较大视觉改版交付时，同时提供手机与电脑的实际画面，以及核心物件或关键动作的截图/短录屏，说明参考版本、资源完成范围和仍使用占位的部分。图稿不能代替运行画面；未完成主要物件美术或关键操作反馈时，不宣称棋桌体验已完成。
