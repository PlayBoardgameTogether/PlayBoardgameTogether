## 本轮新增证据

扩展既有 `tests/integration/official-ai.test.ts`，继续使用真实 session、原房间/开局/动作事务、PostgreSQL、AI 调度器与付款身份。只替换测试模型适配器的返回值，不伪造账本或终局状态。

- **Color Match 完整正式局与账单核对**：管理员发布测试 token 档位，输入/输出基础点价分别 1000/2000 点/百万 token，加价 25%，单次预留上限 6 点；玩家显式设置每席位单局上限 8 点并获得 20 点。每次受控有效回复报告输入/输出各 1000 token，按既有整数公式每次扣 4 点。通过原电脑开局入口建房并完成对局，真人行动使用本人 View 中的合法兜底动作。
- 该次完整局实际 **24 次行动，12 次成功自动行动，其中 2 次模型计费、10 次免费脚本**；共扣 **8 点**，余额 **12 点**，无残留预留。测试核对两条独立账本记录、冻结用量、按局汇总的 2000/2000 token 和 2 个计费行动；逐条关联原调用 requestId、成功 task、applied_revision 与持久化 match_action。达到上限后不再调用模型、不提高上限，结束后房间回到 waiting。其他账户传入同一 matchId 仍无法读取付款人的流水或汇总。行动总数随合法随机开局变化，不将本次 24 次固定成断言。
- **真人收回后的迟到有效回复**：模型返回前确认已预留 6 点，真人通过原控制器接口收回控制，再释放受控有效 choiceId/用量回复。调度器关闭并完成原恢复扫描后，余额仍 20 点、预留为零、reservation 为 released；revision 保持 0、无动作、无消费流水或按局消费账单。

已有回归本轮实际复验：固定/token 计价、整数结算、零费用、用量缺失/不完整/超预留、非法 choiceId、过期与未知请求恢复、并发钱包预留、账本失败时 State/RNG/回执与扣费共同回滚、原提案恢复不重复扣点、目录替换/删除后的旧价冻结、零余额/到达单局上限后的免费脚本与补点恢复、本人账单分页和游标隔离。

夹具类型整理限定于同一测试文件：HTTP 注入载荷使用对象并按需省略 payload；通过现有 `ModelAdapter` 接口描述 mock 返回值；账单用共享 schema 解析。没有扩大 any、关闭严格类型检查或修改生产 mock 接入限制。

## 真实供应商联调入口与待补条件

需要用户明确提供**已有官方档位/可用模型配置、测试付款账户、供应商货币费用上限及最多调用次数**；不要将 API key、会话或验证码写入聊天、提交、日志或验收报告。AI 点数上限不等于供应商货币上限，失败/缺用量/超预留的上游成本仍由平台承担。开始前须确认供应商侧可执行的费用限制或足够小的专用测试额度；不能仅换算玩家点数就声称货币费用受控。

1. 在隔离验收环境使用原模型设置与管理员官方目录配置真实来源，确认 endpoint/model、凭证可用及调用次数/费用范围；连接测试也算真实请求，须计入授权。保留公网 HTTPS、SSRF、凭证加密和原生产禁止 mock 限制，不把真实密钥放入本轮 mock 夹具。
2. 通过原官方点数发放/启用/电脑开局链路，为专用测试付款账户分配有限点数与明确每席位上限，只开一局、一个官方席位；记录开始余额和预留。选择 Color Match 等既有支持 AI 的游戏，不向身份演示扩展补假 AI 能力。
3. 在授权范围内完成最小真实模型行动和完整对局；接近费用/调用上限时通过既有控制/配置流程停止进一步官方请求，免费脚本继续的部分单独记录。若响应超时、缺失用量、格式错误或费用超过预留，立即停止继续联调，核对上游实际消费，不凭玩家未扣点反复发起请求。
4. 按本轮关联关系核对成功 task、供应商 requestId、实际 input/output token、冻结价格、账本、本人按局汇总、终局结果/回放和预留归零；对照供应商用量/货币记录。只保留非秘密摘要，不把原始私密 View、密钥或完整供应商响应写入公开证据。
5. 分别记录真实成功、失败/兜底和未验证部分。受控注入的过期、未知、回滚故障矩阵继续作为本地回归，不为模拟故障增加无授权真实请求；真实供应商通过后再补记 D23 外部验收结论。

计费语义与公式见 [官方 AI](official-ai.md)、[AI 契约](ai-contract.md) 和 [ADR-008](adr/008-official-ai-token-pricing.md)。
