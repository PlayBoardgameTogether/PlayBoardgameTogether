# D27 更新失败恢复演练

2026 年 11 月 22 日（北京时间），在 Windows 本机隔离环境提前完成「候选启动后无法就绪」场景。使用已重新获取的 `main` 提交 `37bd6d59f89ffa1f8c01d7b5be83bd4a38fd9dce`，平台版本 1.4.1。D26 的 [PR #89](https://github.com/PlayBoardgameTogether/PlayBoardgameTogether/pull/89) 独立待审，本次演练使用 main 上已有的诊断能力。

## 演练条件

- 独立 PostgreSQL 17.12 实例仅监听回环端口 17447。原 `prepare-test-db.ts` 检查并创建 `playboard_d27_test_20261122`，与维护库使用不同库名。原迁移和游戏同步脚本以 `--test` 运行，确认 41 条迁移记录。三个账号、对局、备份和资源均为本轮测试数据。
- 旧版构建通过冻结离线安装和 `pnpm --config.verify-deps-before-run=false build`。本地测试 Git 分支从该提交派生，候选 `9108dbf059933bb71cd76feaba0b1671af7312a0` 只将候选 API 的 `/health/ready` 固定为 HTTP 503。监督程序保持原样，演练缓存只从本机测试分支取件。
- 使用平台示例 ZIP `online.score-race@1.0.0`，通过真实管理员 API 安装。另放置一个私有测试资源文件用于验证备份字节；ZIP 桌面资源通过原公开路由进行哈希核对。

## 实测结果

| 验证项 | 实际结果 |
| --- | --- |
| 切换 | 管理员发起检测获 HTTP 202。监督程序独立构建候选、排空旧进程、备份、检查迁移并同步游戏。旧对局连接收到 WebSocket 关闭码 1012，维护期入口返回 HTTP 503 和 `Retry-After: 3`。 |
| 备份 | 实际执行 PostgreSQL 17.12 的 `pg_dump` 和 `pg_restore --list`。既有验证工具核对 **4 个文件、164,633 字节**，包括归档签名、完整清单、资源测试字节和旧版/候选完整 SHA。 |
| 候选及旧版就绪 | 直接在私有 API 端口观测到候选 HTTP 503。北京时间 **10:50:22**，日志与管理员状态一致报告 `stage=start`、`reason=readiness`。入口恢复 HTTP 200、`database.ready=true`，管理员状态报告运行 SHA 仍为 `37bd6d5`，平台 1.4.1。以首发目录启动的演练前后均没有 `current.json`，候选没有被写成已激活版本。 |
| 对局恢复 | 原两名玩家在恢复后以原会话读取第 1 步的本人视图，重新订阅 WebSocket 仍收到第 1 步。对局版本、状态和 RNG 摘要、行动数、迁移数、安装包摘要及桌面响应字节保持一致。重复提交旧请求返回第 1 步，未增加行动记录。随后第 2 步经真实 WebSocket 投递，原局继续到第 7 步完局，两名参与者分别读取初始和终局回放。 |
