# UI/UX 设计规范

本规范由根目录 [AGENTS.md](../AGENTS.md) 按任务引用。适用于玩家页面、房间、游戏桌面与后台的 UI 工作；当前实现入口见 [界面系统](ui-system.md)，运行与回归方式见 [UI 开发与回归](ui-development.md)。本文件规定设计与验收方法，不代表授权全站改版或实现路线图。

## 适用原则与任务分级

设计建议是默认原则，允许为具体用户任务作有依据的调整。可读性、任务效率、可发现性和无障碍优先于风格偏好；不按 Card、按钮、区域或任务数量机械判定设计好坏。代理可在本轮范围内自主选择并简述取舍，无需为普通可逆选择等待批准；身份、私密视图、事务和运行隔离等硬约束仍按根指引执行。

小型文案、间距、颜色或明确组件修复：检查相关页面、调用者、既有 Token 和测试，直接作最小修改，再验证受影响状态与视口。纯后端、测试和文档工作不要求输出设计方案。

新增一级页面、新游戏主界面、复杂房间流程、全局导航变更或较大布局/视觉修改，编码前需覆盖以下流程的设计问题。前四步可以合并成简要说明；已有设计稿、确认方案或成熟组件模式直接复用，只补齐本轮缺项。线框可以用文字或简图表达，不强制另交设计稿，也不为走完流程重新论证已有结论。

1. **分析与目标**：检查现有页面、入口和测试；明确用户是谁、为什么来、主要任务、当前问题，以及第一眼应看到什么。
2. **信息架构**：列出现有功能及内容取舍；说明哪些保留、哪些移动到菜单/Dialog/Drawer/二级页，给出页面与路由结构。没有必要时不新增路由。
3. **核心流程**：描述从进入到完成任务的步骤，以及加载、空状态、失败、提交中、恢复时的行为；删去不必要的确认和绕路。
4. **线框与视觉方向**：明确桌面/手机的区域比例、顺序、主要操作位置；确定气质、配色、背景与表面、字体层级、Artwork、圆角、阴影、动效和密度。
5. **编码**：复用平台组件、主题变量和样式层，保持游戏扩展所有权；需要新 Token 时在对应体系中补齐。
6. **浏览器验收与优化**：实际运行，检查关键视口、状态、键盘与主题，再按下方清单简化；如实记录证据和限制。

已有页面优先延续已确定的视觉方向。建立新视觉体系或用户要求探索时，通常比较 2～3 个有实质差异的方向，例如温暖社交的数字桌游俱乐部、Artwork 主导的现代游戏平台、棋桌主导的沉浸空间；需求已明确时可直接选定并说明适合之处。代理可自主选择，无需每次等待用户批准；用户已有选择时直接沿用，组合视觉元素时保持一致的层级与语言。

## 页面职责与信息架构

页面默认围绕一个核心任务，当前状态下有清晰的操作与视觉层级。棋桌、多步表单等可承载紧密关联的任务；游戏可有多个合法动作，不为满足数量规则隐藏必要信息或强加确认步骤。选择、草稿和确认是否需要，由游戏规则、误操作成本与已有交互决定。

| 层级 | 核心任务与视觉焦点 | 辅助内容的处理 |
| --- | --- | --- |
| 玩家平台 | 发现游戏、进入房间或联系朋友；突出封面、最近游玩与相关玩家 | 搜索、个人设置、通知按任务提供入口，避免把所有功能放在首页 |
| 房间 | 确认游戏、玩家、席位、房主和准备状态，完成准备/开局 | 邀请入口易找；邀请码细节、权限、高级参数与 AI 配置按需展开 |
| 游戏 | 理解局面并完成行动；棋盘/卡牌优先 | 平台导航弱化，规则、声音、控制设置收纳；连接异常和动作结果保持可见 |
| 管理员后台 | 准确查询、审核、配置与处理问题 | 可用表格、筛选、统计与分组导航；危险操作有明确影响说明及确认 |

优先采用熟悉的交互：头像打开用户菜单，齿轮表示设置，更多菜单收纳低频操作；Tabs 用于同一对象的不同视图，Dialog 用于短暂操作，Drawer 用于辅助配置，复杂任务使用独立页。不要只因组件库有现成布局就选用它。

如果用户必须同时理解较多区域，检查能否拆分任务或渐进展示；3～5 个区域是审查提示，不是上限。不要机械增加 Card/Panel，也不要为了减少页面元素把常用操作藏到难以发现的位置。低频但关键的功能可以保持可见。

## 品牌与视觉层级

玩家平台默认表现游戏、社交、收藏和桌面氛围，轻松而有品质；避免无依据地套用低龄卡通、手游商城、电竞直播或通用 SaaS 模板外观。具体游戏主题与用户明确风格要求可有不同表达；品牌目标不能牺牲阅读、任务效率和无障碍。不直接复制某个产品。

- 第一眼能辨认页面任务；标题、核心内容、主要操作和辅助信息有明显层级，不让所有区域同等醒目。
- 游戏封面、横幅和 Artwork 是一级内容，有合适资源时主动利用；不把封面缩成图标后用大量说明填满页面。
- 分组优先通过留白、排版和背景层级，再考虑 Divider 与 Card。游戏、房间、玩家等独立对象适合 Card；两行说明、属性、普通设置和单个按钮通常不需要。
- 按钮使用主要、次要、Ghost、文字/菜单与危险操作层级；图标只用于通用含义或帮助扫描，不给每行文字加图标。
- 不默认套用纯白/浅灰背景、统一大圆角卡片网格、紫色渐变、大量图标、无意义光斑与永久侧栏组合。单项样式不是禁令；已有亮/暗主题、合理后台布局及用户指定风格继续保留。
- 可以使用低对比纹理、环境光、棋盘材质、深度与克制动画，但不能影响阅读、性能或移动交互。不要用害怕留白作为填充内容的理由。

## 平台一致性与游戏自由度

平台统一基础 Typography、导航、菜单、Dialog、Toast、身份、系统状态和无障碍规范。游戏自行决定棋盘、手牌、卡牌比例、资源区、HUD、回合表达、主题色、动画和操作位置。

不要让平台样式侵入游戏桌面，也不要将具体游戏字段或规则写入公共平台布局。平台提供骨架，游戏拥有舞台。

## 实现入口与 Token

先读 [界面系统](ui-system.md) 的最新章节，核对实际文件后修改。历史章节保留旧事实，不以旧加载顺序覆盖当前 CSS layer。

| 入口 | 用途 |
| --- | --- |
| [styles/index.css](../apps/web/src/styles/index.css) | 唯一平台样式入口与 layer 顺序：foundation/platform/components/games/shell/theme |
| [stage9.css](../apps/web/src/styles/stage9.css)、[themes.css](../apps/web/src/styles/themes.css)、[theme-refresh.css](../apps/web/src/styles/theme-refresh.css) | 既有基础变量、亮/暗主题与表面适配；新增前检索同类变量 |
| [共享 UI](../packages/ui/src/index.tsx) | 既有按钮、反馈、状态与错误隔离组件；默认外观不是最终设计依据 |
| [game-registry.tsx](../apps/web/src/game-registry.tsx) | 游戏客户端装配入口；各游戏 client 目录拥有桌面样式 |

复用 `--bg`、`--panel`、`--panel-raised`、`--text`、`--muted`、`--line`、`--accent`、语义状态色和既有间距/圆角/动效变量。平台至少具备背景、表面、正文/次要文字、边界、强调及成功/警示/错误语义；字体区分展示、页标题、分区标题、正文、辅助文字和按钮。按需求补充缺失层级，不为满足清单另建平行 Token 系统。

新增规则放入明确所属 layer，限定组件选择器，不用普通布局 `!important` 或随机 margin 覆盖优先级。游戏按需加载自己的 CSS，使用 `--platform-top-inset` 避让导航，不猜固定导航高度。

## 响应式、无障碍与动效

- 手机重新安排信息顺序和操作路径，可用 Bottom Sheet、Drawer、横向手牌或 Sticky Action；不将桌面三列机械堆成几十个区域，也不让固定操作挡住棋盘或反馈。
- 表单有 label，图标按钮有可访问名称；颜色状态同时用文字/形状表达，错误与必要行动反馈可被辅助技术感知。
- 核心任务可用键盘完成，焦点清晰且顺序合理；自制弹窗管理进入、约束及关闭后的焦点，支持 Escape；菜单按对应控件语义交互。复用原生语义优先于重造控件。
- 控件触摸区域原则上至少 44px；检查文字放大、长名称、窄屏及横屏，避免溢出或不可达操作。
- 动效用于空间关系、加入/准备/行动/结算的状态变化和操作反馈，应快、克制、可预测、不阻塞操作。避免循环闪烁、全页飞入、大量 Bounce 和无意义粒子。
- 尊重 `prefers-reduced-motion`，触屏不依赖 Hover；监听、计时器与观察器有清理入口。游戏动画和音效只消费本人已投影事件，遵守根指引的 live/catch-up 与去重要求。

## 浏览器验收与交付

按根指引选择必要测试；UI 不能只用 typecheck 作为验收。中大型布局或全局样式修改实际检查桌面（如 1440×900）、常见笔记本（如 1280×800）与手机（如 390×844）；小型修复检查受影响状态、视口与必要相邻断点。窄屏、横屏或复杂棋桌再检查 320px、844×390 等受影响尺寸。示例尺寸不是固定配额，模拟视口与真实设备分别记录。

检查核心任务、主操作、视觉焦点、对齐、文字层级、密度与留白；覆盖适用的加载、空、错误、禁用、提交中、离线和恢复状态，并检查亮/暗主题、键盘焦点与减少动态效果。真实身份、房间和联机流程按现有 E2E 验证，固定场景只用于视觉检查。

最后尝试减少约 20% 的非必要元素：重复标题/说明、无意义边框/图标、套叠 Card、常驻低频按钮。如果简化后更清楚就保留；这不是硬性配额，不机械删除品牌 Artwork、空间层级、必要状态或无障碍信息。

玩家页面隐藏 Logo 后若仍与任意 SaaS 模板无区别，检查是否缺少游戏内容、版式与环境表达；后台不套用此判断。最终交付写明实际检查页面、尺寸/方法、测试结果及未验证项，不能把未启动的浏览器或未调用成功的服务计为通过。
